## 1. 학습 내용

### 1-1. 멀티 소스 데이터 파이프라인 설계

Supabase(기존 ai_test 테이블)와 Supabase2(articles + comments 테이블)라는 서로 다른 DB 소스에서 데이터를 로드하고, 하나의 파이프라인으로 통합 처리하는 구조를 학습했다. 단순 SELECT가 아닌 1,000건 단위 페이지네이션이 필요했고, Supabase Python SDK의 `.range()` 방식으로 전체 데이터를 누락 없이 불러오는 방법을 익혔다.

### 1-2. 이기종 모델 협업 아키텍처

단일 LLM이 아닌 **로컬 모델 + Groq API + Gemini API** 세 가지를 피처 성격에 따라 분담시키는 구조를 설계했다.

| 처리 주체 | 담당 피처 | 선택 이유 |
|-----------|-----------|-----------|
| 로컬 HuggingFace | stance_score, cmt_emotion, loaded_words, body_depth | API 비용 없음, 속도 우선 |
| Groq (Llama 3.3 70B) | frame, logic, bias_x/y | 구조화 추론 품질 |
| Gemini Pro | omission_risk | 긴 컨텍스트 + 고품질 판단 |

각 모델의 특성과 API 제약(RPM/RPD 한도)을 파악하며, 어떤 작업에 어떤 모델을 써야 하는지 직접 판단 기준을 세우는 경험을 했다.

### 1-3. API 클라이언트 안정화 기법

실제 프로덕션에서 LLM API를 안정적으로 운영하는 데 필요한 기법들을 직접 구현하며 학습했다.

- **다중 API 키 로테이션**: 한 번 소진된 키는 재사용하지 않는 단방향 진행 방식으로 rate limit 회피
- **모델 폴백**: 특정 모델 실패 시 자동으로 다음 모델로 전환 (llama-3.3-70b → llama-3.1-8b 등)
- **강건한 JSON 파싱 4단계**: LLM이 JSON을 깨뜨리는 패턴(마크다운 코드펜스, 후행 쉼표, 단따옴표, `<think>` 블록 등)을 식별하고 각각에 대응하는 전처리 로직 구현
- **배치 실패 시 1개씩 재시도(폴백)**: 20개 배치가 실패하면 1개씩 재처리하여 성공 가능한 기사는 손실 없이 처리

### 1-4. 한국어 NLP 특수성 대응

- **`\b` 단어 경계 정규식**: 영어에서는 동작하지만 한국어에서는 작동하지 않음을 확인, 한국어 형태소 경계를 고려한 대안 패턴으로 교체
- **LLM 한글 오자 문제**: llama-4-scout 모델이 한국어 레이블을 오자로 출력하는 현상을 발견, 프롬프트를 "한글 텍스트 출력 금지 + 숫자(1~7)만 출력"으로 변경하여 완전히 회피
- **부분 매칭 복구 로직**: 출력된 레이블이 정확히 일치하지 않아도 4단계(exact → index → partial → 유사도 0.40 이상) 매칭으로 복구

### 1-5. 병렬 처리 및 성능 최적화

- `ThreadPoolExecutor`로 Groq와 Gemini 처리를 동시에 실행 (순차 → 병렬, max_workers=2)
- 댓글 처리도 기사 단위 병렬화(`--cmt_workers` 옵션)
- batch_size를 5 → 20으로 확대하고 프롬프트 동적 압축 적용
- O(n²) 복잡도였던 NER 클러스터링을 각 기사별 1회 실행 + 공통 엔티티 재사용 방식으로 개선

### 1-6. DB 업로드 및 Upsert 전략

Supabase2의 `article_features` 테이블에 unique constraint가 없어 단순 upsert가 불가능한 문제를 마주쳤다. **SELECT → PK 주입 → upsert** 패턴을 직접 설계하여 해결했다. 또한 frame/logic 레이블 문자열을 DB 스키마에 맞는 정수(1~7, 1~6)로 매핑하는 하드코딩 딕셔너리를 구현했다.

### 1-7. 디렉토리 리팩토링 및 Python 패키지 구조

`feature_map/stance/src/feature_map/preprocessor.py` 같은 4단계 중첩 경로와 `sys.path`를 런타임에 조작하는 구조적 문제를 인식하고, `labeling/features/`라는 단일 패키지로 통합했다. 올바른 Python 패키지 구조(`__init__.py`, 상대 import)를 적용하여 `from labeling.features.preprocessor import build_article_struct` 형태의 깔끔한 import로 전환했다.

### 1-8. 실험 프레임워크 설계

모델 파라미터를 "감으로" 바꾸는 방식의 한계를 인식하고, 재현 가능한 실험 환경을 구축했다.

- **규칙 기반 튜너**: body_depth(가중치 5개 × 정규화 상수 5개 Grid Search), loaded_words(tier_mode 3종 × 8가지 preset)
- **모델 평가기**: `BaseEvaluator` 추상 클래스 + 피처별 구체 클래스, Pearson/Spearman/MAE(연속형), F1-macro/Cohen's Kappa/혼동행렬(범주형) 메트릭 지원
- **Ground Truth 기반 평가**: JSONL 포맷 정답 데이터를 기준으로 예측 결과와 자동 비교

## 2. 학습 방법

### 2-1. 문제 발생 → 즉시 문서화 → 해결책 커밋

이슈가 발생할 때마다 `docs/0N_issues_*.md`에 **문제 상황, 원인, 해결 방법**을 바로 기록했다. 단순히 고치는 데서 끝나지 않고 왜 발생했는지를 추적하는 습관을 들였다. 총 8개의 이슈 로그 파일에 25건 이상의 문제-해결 쌍이 축적됐다.

### 2-2. 반복적 파이프라인 실행 + 실패 분석

실제 키워드(예: `종소세`, `방탄광화문`)로 파이프라인을 반복 실행하며 실패 케이스를 수집했다. API 오류, JSON 파싱 실패, DB upsert 충돌 등 실서비스 수준의 엣지케이스를 직접 마주쳤고 각각 방어 로직을 추가했다.

### 2-3. 코드 단계별 분리 설계 (관심사 분리)

하나의 파일에 모든 로직을 넣지 않고, 역할에 따라 다음처럼 계층을 나눠 설계했다:

```
features/        ← 모델 없는 순수 텍스트 추출
local/           ← 로컬 HuggingFace 모델 래퍼
groq/ / gemini/  ← API 클라이언트 + 라벨러
run_labeling.py  ← 오케스트레이션 (연결만 담당)
upload_to_db.py  ← 저장 단계 분리
```

각 레이어가 독립적으로 교체 가능하도록 인터페이스를 통일했다(`label_XXX_batch(items) → list[dict]` 규격).

### 2-4. 점진적 리팩토링

동작하는 코드를 먼저 만들고, 이후 구조적 문제가 보이면 단계적으로 개선했다. 기능 추가 → 테스트 → 이슈 발견 → 리팩토링 → 문서화의 사이클을 반복했다. `sys.path` 해킹처럼 빠른 해결책(quick fix)이 나중에 더 큰 문제를 만든다는 것을 실제로 경험했다.

### 2-5. 아키텍처 결정 기록 (ADR)

설계를 바꿀 때마다 `05_architecture_decisions.md`에 **무엇을 왜 결정했는지**를 남겼다. 나중에 동일한 고민이 반복되는 것을 방지하고, 팀원이 코드를 볼 때 맥락을 파악할 수 있도록 했다.

## 3. 학습 성과 및 목표 달성도

### 3-1. 핵심 성과

#### ✅ 엔드-투-엔드 라벨링 파이프라인 완성
Supabase에서 기사를 로드하여 9개 피처를 자동으로 라벨링하고 Supabase2에 업로드하는 전체 흐름이 실제로 동작한다. 단일 커맨드로 수백 건의 기사를 처리할 수 있다.

```bash
# 기사 라벨링
python AI/labeling/run_labeling.py --keyword 종소세 --features all

# DB 업로드
python AI/labeling/upload_to_db.py --mode all --keyword 종소세
```

#### ✅ API 안정성 확보
초기에는 rate limit, JSON 파싱 실패, 키 소진 등으로 파이프라인이 중간에 멈추는 일이 잦았다. 현재는 키 로테이션, 모델 폴백, 배치 실패 시 1개씩 재시도, 부분 결과 즉시 저장이 모두 구현되어 긴 배치 처리도 안정적으로 완료된다.

#### ✅ 코드베이스 구조 정리
- `feature_map/` (63개 파일) 전체 삭제 — `labeling/features/`로 통합 완료
- `sys.path` 런타임 조작 코드 완전 제거
- 미사용 파일(`frame_logic_labeler.py`, `bias_vector.py`, `omission_risk.py`) 정리
- 6단계 의미 있는 커밋으로 변경 이력 추적 가능

#### ✅ 실험 프레임워크 기반 마련
지금까지 rule-based 파라미터를 근거 없이 설정했던 문제를 해결하는 인프라가 갖춰졌다. Ground Truth 데이터만 수집하면 즉시 체계적인 성능 평가와 하이퍼파라미터 탐색이 가능하다.

#### ✅ 문서화 체계 구축
| 문서 유형 | 파일 수 | 내용 |
|-----------|---------|------|
| 이슈 로그 | 8개 | 발생한 모든 버그와 해결책 |
| 모듈 문서 | 4개 | 함수 시그니처, 입출력 예시 |
| 파이프라인 문서 | 2개 | 전체 흐름도, Mermaid 다이어그램 |
| 아키텍처 결정 | 1개 | 설계 의사결정 근거 |

### 3-2. 목표 달성도

| 목표 | 달성 여부 | 비고 |
|------|-----------|------|
| 기사 라벨링 파이프라인 실행 가능 | ✅ 완료 | 9개 피처 전체 처리 |
| 댓글 감정 + 편향 단어 라벨링 | ✅ 완료 | 병렬 처리 지원 |

| 코드 구조 리팩토링 | ✅ 완료 | feature_map 완전 제거 |

### 3-3. 다음 주 목표

1. **Ground Truth 데이터 수집**: 기사 50~100건에 대해 frame, logic, bias, omission_risk 수작업 레이블링
2. **body_depth Grid Search 실행**: 수집된 GT 기준으로 최적 가중치 조합 탐색
3. **frame / logic 모델 정량 평가**: F1-macro, Cohen's Kappa 측정 및 오류 케이스 분석
4. **loaded_words tier 최적화**: word_freq 분석으로 현재 사전 품질 점검
